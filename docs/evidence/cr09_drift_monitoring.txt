===========================================================================
1. The problem this solves
===========================================================================
Part 1 built the drift check: it compares the journal against the database and reports
differences. Reporting once, on demand, is not monitoring. A detector that is never run finds
nothing, and one that alerts on every pass is worse than useless.

The design constraint is in the gate's own wording: "MEASURED false alerts". So the monitor
alerts on TRANSITIONS rather than on state:

  first drift detected            -> WARNING
  still drifting                  -> silence, unless the reminder cadence is due
  drifted for `escalate_after`    -> CRITICAL, once, because a drift that does not clear by
     consecutive checks              itself is a different situation from one that comes and goes
  drift clears                    -> INFO recovery alert, so the operator does not have to
                                     re-check to find out

Each alert carries `occurrences`, and the monitor exposes `alert_rate()`, so the false-alert
rate is a number read from the journal afterwards rather than an impression.

===========================================================================
3. Measured alert rate, not asserted
===========================================================================
Twenty checks of one unresolved drift produce exactly TWO alerts:

  check 1   announcement   WARNING
  check 2   silence
  check 3   escalation     CRITICAL
  checks 4-20               silence (no reminder due at the same instant)

  alerts_per_drifted_check = 0.10

A reminder cadence of 900s adds one alert per 15 minutes while the drift persists, which is
what keeps a long outage from being silent without making it unreadable. A second test lowers
the cadence to 1s and asserts the rate goes ABOVE 0.5, so the shouting failure mode is visible
in the measurement too. Both directions are covered because both are failures.

===========================================================================
4. What the monitor deliberately does NOT do
===========================================================================
  * It never REPAIRS drift. A divergence means we do not know which record is wrong, so
    overwriting either would destroy the evidence needed to find out (ADR-0004 s5). Tested:
    the database is untouched after a drift check.
  * It never HALTS. It reports `blocks_new_exposure` as a fact; the watchdog decides what to
    do about it. Giving a second component the power to halt would create a second place for
    a halt to be wrong. Tested: a drifting monitor leaves RiskState untouched.
  * It never emits when given no emitter. A read-only inspection is a legitimate use, and a
    caller who only wants to know whether the two agree should not have to open the journal
    for append to find out.

That last point is a real design trap, and it is why the CLI passes no emitter. Emitting the
alert INTO the journal would append an event the database does not yet have, so the NEXT
drift check would report drift caused by the monitor itself - a false positive generated by
the very component meant to detect problems.

===========================================================================
5. Determinism
===========================================================================
The monitor holds no clock. The instant of each check is passed in, so a test drives twenty
checks in a millisecond and a replay reproduces exactly which alerts fired and when.
`interval_runner` takes an injected Clock and advances it itself rather than sleeping, so the
cadence logic is tested rather than assumed. The deployment scheduler calls
`DriftMonitor.check` directly.

7. Limitations
===========================================================================
1. The cadence is driven by the caller. There is no long-running daemon, no systemd unit and
   no container for it; `--interval-seconds` loops in the CLI process. A real deployment needs
   the process supervised.
2. Alerts are journaled but not routed. There is no email, webhook or pager integration, and
   no alert deduplication across processes - two monitors watching one journal would each
   alert.
3. The gate's other items are still open: long-duration paper/shadow runs (blocked on CR-03's
   write-scoped grant for real paper evidence), latency and P&L attribution reporting, and the
   incident runbooks.
4. `--allow-gaps` remains available on `project` for inspecting a known-damaged journal. Using
   it on a healthy one would hide exactly the condition this monitor exists to find.
