Generated: see the git commit this file was added in

This closes the last gap CR-05 had named: nothing actually *fetched* anything.

===========================================================================
1. The three separations that carry the safety of this module
===========================================================================
A. A CONNECTOR PRODUCES DOCUMENTS, NOT FACTS.
   RawDocument is untrusted text plus provenance. Turning it into a Fact -- assigning the
   fact id, hashing content, stamping availability -- happens in IngestionPipeline, in one
   place. The connector has no store, no registry and no clock, so it CANNOT mint a fact id,
   backdate availability, or mark its own content clean. Tested by asserting the connector's
   public surface contains none of those.

B. available_at IS STAMPED AT INGESTION, NEVER TAKEN FROM THE SOURCE.
   The source's own timestamp says when they claim they published it. What matters for
   lookahead is when WE could first have acted on it. Verified:
       published_at = 2026-03-02T14:30:00+00:00   (the source's claim)
       available_at = 2026-03-02T14:40:00+00:00   (the injected clock at ingestion)
   Stamping available_at from published_at would let a feed backdate its own content into the
   past, which is exactly the lookahead this project is built to prevent.

C. A CONNECTOR THAT CANNOT BE VERIFIED REFUSES TO RUN.
   Market-data entitlements are UNVERIFIED in this project. HttpNewsConnector raises rather
   than fetching, and says what would be needed:
       "refusing to fetch 'https://...': no market-data entitlement has been confirmed for
        this feed. Entitlements are a commercial fact, not a code fact ... Set
        entitlement_reference to the written confirmation before this connector will run."
   With an entitlement it STILL refuses, because there is no fetcher: a fetcher that has never
   run against a real endpoint is untested code wearing a working label (AGENTS.md inv. 11).

3. What the pipeline enforces, and what it refuses
===========================================================================
  [x] source must be REGISTERED            -> provenance, reliability and licence scope are
                                              declared, not asserted by the connector
  [x] connector may only return ITS OWN source's documents  -> blocks smuggling
  [x] published_at in the future is REJECTED (beyond 5 min of tolerated skew)
  [x] empty documents are rejected
  [x] injection patterns are FLAGGED and travel with the fact, not silently stripped
  [x] ingestion is idempotent for identical bytes
  [x] the content hash covers the cleaned text, and the external id is included so two
      different documents sharing a body stay distinct

===========================================================================
4. A lookahead guard in the Fact model that this pipeline tripped, correctly
===========================================================================
A source whose clock ran one minute fast produced a pydantic ValidationError: the Fact model
refuses a fact whose event_time is later than its available_at. That is CORRECT -- a fact whose
event precedes our knowledge of it IS lookahead -- and the fix belongs in the ingestion path,
not in the model: event_time is now min(published, now), so it can never be later than the
moment we learned of it, while published_at keeps the source's own claim and
attributes["published_ahead_of_ingestion"] records that the two differed. Tolerance is five
minutes, because a minute of skew between us and a publisher is normal rather than an attack.

===========================================================================
5. A claim I had to withdraw rather than make true
===========================================================================
The first version stripped the cleaned text before hashing and claimed that made a reformatted
refetch idempotent. It does not. Leading whitespace on a BODY becomes INTERIOR whitespace once
the title and body are joined, so stripping the ends changes nothing. Folding interior
whitespace would have made the claim true at the cost of conflating documents that genuinely
differ -- the wrong trade for an evidence store.

So the claim is withdrawn and the real behaviour asserted instead: an identical refetch is a
duplicate, and a refetch whose content changed produces a DISTINCT fact. That exposes a real
gap rather than hiding one, and it is recorded below.

7. Revision chaining (added after this file was first written)
===========================================================================
The gap recorded in the limitations has been closed. It was real: before chaining, a feed that
re-served an article with a corrected figure left TWO facts that both looked current, and a
snapshot could cite either. The Fact schema already anticipated this -- supersedes, vintages()
and effective_fact() all existed -- and the field was left None.

The rule now: a revision is the same DOCUMENT (same source, same external id) with different
CONTENT. Identical content stays a duplicate; a different document starts its own chain.

    $ ingest "Chipmaker raises guidance to 5.10."
    fixture-news: fetched 1, admitted 1, duplicates 0
    $ ingest "Chipmaker raises guidance to 5.25 (corrected)."
    fixture-news: fetched 1, admitted 1, duplicates 0, revisions 1

    fact:e9b754e740a6fb22d  supersedes=None
    fact:b8a720fab13f5c8f7  supersedes=fact:e9b754e740a6fb22d

    chain from newest: 3 revisions
    oldest first bodies: ['to 5.10', 'to 5.25 (corrected)', 'to 5.30 (corrected again)']

Three properties worth naming:

  * NOTHING IS OVERWRITTEN. Both revisions are stored; the chain is a link, not an update. The
    store is append-only and stays that way.
  * THE LINK IS MADE BEFORE THE STORE SEES THE FACT, so there is no window in which two
    revisions both look current. That window is exactly what supersedes exists to prevent.
  * INDEXING IS LAZY AND READS THE STORE, so a pipeline started against an existing fact log
    chains onto what is already there rather than treating every document as new. That is the
    case that matters operationally: a restart is exactly when a feed is most likely to
    re-serve something.

And the payoff is not cosmetic: vintages() and effective_fact() now work on ingested content, so
a replay at an earlier instant sees the revision that actually existed then. That was already
true for facts constructed in-process and was the remaining gap for ingested ones.

===========================================================================
8. Limitations
===========================================================================
1. NO REAL FEED HAS BEEN CONTACTED. There is no fetcher, because there is no verified
   entitlement. Every test runs against an in-code fixture connector. The fixture connector is
   labelled SYNTHETIC where it is used and is not a news feed.
2. ~~REVISION CHAINING IS NOT IMPLEMENTED.~~ **CLOSED.** See section 7.
3. No scheduling. Ingestion runs when a caller invokes it; there is no poller, no backoff and
   no rate limiting, and a real feed would need all three.
4. Only news-shaped documents. There is no connector for filings, earnings calendars or
   corporate actions, though SourceKind already has OFFICIAL_FILING.
5. The fixture connector filters by the fetch window, so a future-dated document is dropped
   by the window before the pipeline's own future check sees it. The check is still correct
   and is tested directly by driving the pipeline with a widened window; the ordering is
   recorded here because it surprised me.
