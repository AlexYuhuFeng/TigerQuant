3. ADR-0010 was right: the documentation is unusable for this version
===========================================================================
Reading the .pyx that ships INSIDE the wheel found two differences that would each have made
the adapter silently non-functional:

  DOCUMENTED (v2 line)                  ACTUAL 1.231.0
  ------------------------------------  --------------------------------------------------
  __init__(loop, client_id, venue,      __init__(client_id, venue, oms_type, account_type,
           msgbus, cache, clock, ...)            base_currency, msgbus, cache, clock,
                                                 config=None)
  async def _submit_order(command)      cpdef void submit_order(SubmitOrder command)
  async def _cancel_order(command)      cpdef void cancel_order(CancelOrder command)

An adapter written from the guides would have imported cleanly and never intercepted a single
order: the private coroutine names do not exist, so nothing would have been called.

One more fact taken from the source rather than guessed: ExecutionClient.__init__ documents
that it raises ValueError unless `client_id == account_id.get_issuer()`. The first attempt used
AccountId("TIGER-PAPER") and failed with exactly that. It is now AccountId(f"{client_id}-PAPER").

All of this is pinned in compat.py, so a wheel bump that moves a class, renames a method or
changes the environment enum fails loudly instead of drifting.

5. Live construction and gating, verified
===========================================================================
$ python - <<'PY'   (injected broker that throws if submit is ever reached)
client = build_execution_client(broker=NeverCalledBroker(), approvals={},
                               submission_target=SubmissionTarget.NONE, mode=Mode.SHADOW)
client.tq_connect()

CONSTRUCTED TigerQuantExecutionClient
allows submission: False
GATE REFUSED ok, codes: ['MODE_CAPABILITY_ABSENT']
translate ok: True | qty: 8 | side: BUY
PY

Three gates stand between the engine and a venue, and each is tested:

  1. the SUBMISSION GATE, which refuses whenever submission_target is NONE and RECORDS the
     attempt, so a shadow run's would-be orders are visible evidence rather than a silent
     no-op;
  2. the APPROVAL check -- there is no path that submits without an ApprovedOrder. The engine
     is not the risk authority (ADR-0007);
  3. TRANSLATION, which refuses an unknown side, an unsupported order type, a limit order with
     no price, a non-positive quantity, or a missing client order id.

Cancellation is deliberately NOT gated. A halt or a shadow run must always be able to reduce
exposure, and a risk control that can block a cancel is dangerous.

6. Parity harness: contract violations are not venue characteristics
===========================================================================
execution/parity.py drives two BrokerProtocol implementations through an IDENTICAL ordered
command list and classifies every divergence:

  structural  a different step count, state, fill count, or order-id presence. FAILURES: the
              two paths are not implementing the same contract.
  labelled    a different fill price, commission or quantity. EXPECTED between a simulator and
              a real venue, reported with the field and both values rather than hidden.
  timing      the same state with a different message.

The verdict is named `comparable`, deliberately not `equal`, and the summary says so.

A bug the harness found in itself: its QUERY path left average_fill_price as None, so two
venues filling the same quantity at different prices were reported as "identical" -- the exact
smoothing the module promises not to do. Now fixed, and the test that compares two scripted
prices is what caught it.

7. A control this CR had to fix rather than work around
===========================================================================
The privilege-bypass test that asserts "no alternative order path" scanned the source tree for
the literal strings place_order(, submit_order(, and so on. It produced two false positives:
the Nautilus adapter legitimately DEFINES submit_order to satisfy the engine's override points,
and the module's own docstring names the APIs it forbids.

A control that forces code to avoid certain words is a control nobody keeps, so the scan was
rewritten to use the AST and look for CALL nodes. Verified afterwards that it still catches a
real violation: the excluded Tiger adapter genuinely calls place_order and cancel_order, and a
synthetic violation is detected.

9. Limitations
===========================================================================
1. No strategy-loop parity test. This CR proves the execution client's contract; it does not
   run a Nautilus node through the same scenario the internal simulator runs, which is what
   ADR-0010 section 6 actually asks for. That needs the engine's kernel, a data client and a
   strategy registration, which is a larger piece of work than the adapter itself.
2. No parity against a real Tiger paper session, because that needs CR-03's write-scoped grant.
   The two blockers are linked: full CR-04 parity evidence needs both the engine AND the grant.
3. Only the ExecutionClient is implemented. DataClient and InstrumentProvider are pinned by the
   compatibility test but not written -- without a verified market-data entitlement (see the
   CR-05 blockers) there is nothing for a DataClient to load.
4. No committed shared scenario corpus. ADR-0010 section 6 calls for one.
5. The engine is now installed in the development venv, so the `requires_engine` lane runs by
   default. `uv sync --frozen --extra dev` will NOT install it; the extra is `engine`.
