===========================================================================
2. Cause 3, ISOLATED: a snapshot re-digested every cited fact, every bar
===========================================================================
The previous writeup localised the remaining cost to canonicalisation and explicitly said it was
not isolated. Instrumenting `digest_of` to record the SIZE of what it was handed settled it:

    bars   digest calls   max payload   max cited facts
     100          5,360       17,731 B               100
     400         81,798       70,531 B               400

Two things, both decisive:

  * digest CALLS grow as ~0.5 x bars^2 (5360/100^2 = 0.54; 81798/400^2 = 0.51), and
  * the PAYLOAD grows linearly, because `max cited facts` equals the bar count.

The mechanism: `resolve()` emits `res.effective.digest()` for every CITED fact, and the momentum
strategy cites every bar it has seen. So snapshot N digests N facts, and the total is
sum(1..bars) -- quadratic.

CHECKED FOR A CORRECTNESS BUG FIRST, and it is not one: `resolve()` iterates only the cited
`fact_ids`, so a decision's provenance contains the facts it actually used and not the whole
store. It is a strategy that cites a growing window, which is legitimate. The problem was purely
that the same immutable bytes were being digested over and over.

===========================================================================
3. The fix: memoise `Fact.digest()`
===========================================================================
A `Fact` is a frozen pydantic model, so `digest()` is a pure function of state that cannot change.
Computing it once and reusing the result is observationally identical to recomputing it, and
returns the SAME BYTES.

That is the whole reason this fix was safe where changing the digest MATERIAL would not have been.
The snapshot digest embeds this value, and CR-01's baseline journal digest
(5ac9de744ae629f15e5c79a4289f7f60a4db39760431324cfd5899c60c6439d3) pins the snapshot digests.
An optimisation that altered the output would have moved a published baseline.

Evidence that it did not move:

  * `pytest -q` -- 776 passed, unchanged, including every snapshot and evidence-store test;
  * `pytest -q -k "baseline or 5ac9de74 or replay"` -- 27 passed, including the tests that pin the
    CR-01 journal digest.

The cache is keyed by `fact_id` rather than by the object, because a Fact holds a dict attribute
and is therefore unhashable. The key is sound because this project derives `fact_id` from content.
It is bounded at 200,000 entries, evicting the oldest half, so a long run cannot grow it without
limit.

7. Limitations
===========================================================================
1. The scaling is much better but not proven linear: 2.7x per doubling at 400-800 bars. A very
   long run would still be slower than it needs to be, and no further profiling was done past
   this point because the gate no longer requires it.
2. The digest cache is process-local and not shared or persisted. A fresh process re-computes.
3. Cache size is bounded at 200,000 fact digests; past that it evicts, so a very large store
   would see partial re-computation rather than unbounded growth. Not exercised by any test run.
4. The strategy citing every bar it has seen is what made this quadratic. It is legitimate, and
   it is also worth asking separately whether a decision's provenance SHOULD grow without bound --
   that is a design question about evidence scoping, not a performance one, and it is NOT
   addressed here.
