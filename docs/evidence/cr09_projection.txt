Generated: see the git commit this file was added in

Scope: the projector and the drift check. CR-09's full scope (long-duration harness,
runbooks, drift *detector on a schedule*) is not finished; this is the foundation.

===========================================================================
1. What this makes true
===========================================================================
ADR-0013 claims the hash-chained journal is authoritative and PostgreSQL holds *rebuildable*
projections. Until now that was a claim about intent. This module is what makes it a claim
about behaviour: it reconstructs the relational tables from the journal alone, and it
compares what the journal implies against what the database currently says.

===========================================================================
3. Two bugs this work found, both caught by guards that already existed
===========================================================================
These are the most valuable output of the CR, and neither was visible from reading code.

BUG 1 - a replayed projection regressed a completed order back to CREATED.
  The fold starts from a fresh OrderProjection each pass, so on a second run the journal's
  first event re-emitted CREATED for an order the venue had already filled. Writing
  unconditionally would have silently rewound order state on every replay.
  Caught by: the repository's terminal-state guard, which raised
      "order ... is terminal (FILLED) and cannot move to CREATED"
  Fixed by: writing a folded snapshot only when its event is newly appended, or when the
  row is genuinely missing (the rebuild case). Replaying is now a no-op, and the test
  asserts both the report counters AND that portfolio_state is unchanged.

BUG 2 - EventBase.payload is a METHOD, not an attribute.
  The natural-looking getattr(event, "payload", {}) returns a bound method, which is
  truthy, so the failure surfaced much later as
      AttributeError: 'function' object has no attribute 'get'
  far from its cause. Replaced with a single _payload() helper that is the one place
  knowing the difference.

A THIRD near-miss, avoided by not writing a second state machine:
  The order fold is NOT reimplemented in the projector. OrderProjection already owns the
  state machine, and the projector folds with it and persists the result. The first version
  of this module did reimplement it and failed on the live run with
      illegal order transition CREATED -> SUBMITTING
  because the state machine requires CREATED -> RISK_APPROVED -> SUBMITTING and
  RiskEvaluated is the event carrying that transition — a fact a second implementation had
  no way to know. The fix was to delete the duplicate, not to patch it.

===========================================================================
4. Drift is reported, never repaired
===========================================================================
check_drift() compares the journal with the database and returns a report. It does not
adjust either side. A divergence means we do not know which record is wrong, and silently
overwriting one with the other would destroy exactly the evidence needed to find out
(ADR-0004 s5). A test asserts the database is untouched by a drift check.

The two directions are NOT treated as equivalent. Extra events in the database that the
journal lacks get a specific note: the journal is the record of authority, so that direction
means a journal file was truncated or lost, or something wrote to the database directly.

A gapped journal is refused outright rather than projected. A gap means events were lost, and
a projection built from it would be confidently wrong — worse than one that is obviously
incomplete. --allow-gaps exists only for inspecting a known-damaged journal.

===========================================================================
7. Two more bugs the live run exposed
===========================================================================
BUG 3 - the fill projection was UNREACHABLE and silently wrote zero fills.
  OrderPartiallyFilled and OrderFilled belong to BOTH the order-event set and the
  fill-event set: they advance the order state machine AND carry an execution. Written as
      if kind in _ORDER_EVENTS: ...
      elif kind in _FILL_EVENTS: ...
  the second branch could never execute. Everything else looked correct — 31 events, the
  right cash, a consistent drift report — and the only symptom was "0 fill(s)" for a
  scenario whose whole purpose is to fill an order. The fill branch is now nested inside the
  order branch, with a comment saying why it must not be an elif.

BUG 4 - the fill payload did not satisfy the repository's fill contract.
  append_fill needs instrument, side, quantity, price and occurred_at. The event carries the
  execution (exec_id, quantity, price) but NOT the instrument or the side, because those
  belong to the order rather than to the execution. The insert failed with
  KeyError: 'instrument', and the whole projection rolled back — which is the transaction
  boundary doing its job.
  Fixed by enriching the payload from the folded order before storing it, and by refusing to
  write a fill whose order is unknown rather than fabricating an instrument. In the normal
  path the order fold refuses that case first with IllegalOrderTransition, which is stronger.

===========================================================================
8. Limitations
===========================================================================
1. Orders, fills, positions, portfolio state, decisions and risk outcomes are projected and
   verified. Evidence FACTS are not: the fact store is populated by ingestion, not journaled
   as events in the CR-01 event set, so there is nothing in the journal to fold. Alerts are
   projected but the scenarios produce none, so that path is exercised by unit test only.
2. The rebuild case (projections lost, events intact) is handled by the "row is missing"
   branch, but there is no CLI command that drops and rebuilds the tables. Add one before
   relying on it operationally.
3. Drift detection runs when `project` is invoked. There is no schedule, no alerting and no
   independent watchdog hook yet — that is the rest of CR-09.
4. The 20 requires_db tests run against a real container; CI still has no remote runner, so
   no linkable CI run exists.
